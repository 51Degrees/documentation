Metadata

The properties of the data file, with the answers the C++ property metadata gives.

Each function takes a data set from fiftyoneDegreesDataSetHashGet, which the caller holds while it reads so that every answer comes from the same data file. A property is found by its index in the data file, which counts every property the file defines, including those the data set was not created with. A function that gives text writes it into the buffer provided when it fits, and otherwise into memory the caller frees with fiftyoneDegreesFree when the pointer returned is not the buffer, as fiftyoneDegreesStoredBinaryValueToText describes.

◆ fiftyoneDegreesResultsHash

typedef fiftyoneDegreesResultHashArray fiftyoneDegreesResultsHash

Array of Hash results used to easily access and track the size of the array.

The results are used by one thread at a time, because reading a value writes into the results, and when no properties were named the first read of a property of a component walks the component's graph. Different results can be used on different threads at once, and the resource manager can be shared, unless the library is compiled with FIFTYONE_DEGREES_NO_THREADING.

Examples
Hash/MatchMetrics.c, and Hash/StronglyTyped.c.

◆ fiftyoneDegreesHashGetEvidenceKeys()

size_t fiftyoneDegreesHashGetEvidenceKeys ( fiftyoneDegreesDataSetHash * dataSet,
char * buffer,
size_t length,
const char * separator )

Writes the evidence keys the data set accepts, each with its prefix, with the separator between them.

The keys are listed in this order.

  1. For each unique header in the data set that is not a pseudo header, a key under header. and then one under query., with HTTP_ before the header name when the configuration's usesUpperPrefixedHeaders is true. The header name is as the data set holds it.
  2. For each property that can be overridden, a key under cookie. and then one under query., with 51D_ before the property name when the overrides need that prefix.
  3. query.51D_deviceId, query.51D_gethighentropyvalues, query.51D_structureduseragent, cookie.51D_gethighentropyvalues, cookie.51D_structureduseragent, query.51D_ProfileIds and cookie.51D_ProfileIds.

The keys in 2 and 3 are listed only when the configuration's processSpecialEvidence is true, as the data set reads none of them otherwise.

A key that is listed more than once is written where it is first listed. Call with a NULL buffer to find the length needed, then with a buffer one longer than that.

Parameters
dataSetthe data set to list the keys of
bufferto write the keys to, or NULL to only find their length
lengthof the buffer, including room for the null terminator
separatorwritten between keys. A comma suits, as no HTTP header name holds one and property names are given as a comma separated list.
Returns
the number of characters the keys and separators need, not counting the null terminator. When the buffer is shorter than that plus one, it holds as many characters as fit followed by a null terminator.

◆ fiftyoneDegreesHashGetHardwareProfileScript()

size_t fiftyoneDegreesHashGetHardwareProfileScript ( const char * body,
char * buffer,
size_t length )

Writes the script the client runs for a value of the JavascriptHardwareProfile property.

The values the results give for that property are the bodies of the script. A body pushes the ids of the profiles it finds onto an array named profileIds, which it does not declare, and sends them nowhere. The script declares the array, then runs the body, then writes the ids, separated by '|', to the 51D_ProfileIds cookie, which the engine reads as evidence that sets the profiles. An empty or NULL body is written in the same way. Call with a NULL buffer to find the length needed, then with a buffer one longer than that.

Parameters
bodythe value of the property, or NULL for an empty one
bufferto write the script to, or NULL to only find its length
lengthof the buffer, including room for the null terminator
Returns
the number of characters the script needs, not counting the null terminator. When the buffer is shorter than that plus one, it holds as many characters as fit followed by a null terminator, and a buffer of length 0 is left as it is.

◆ fiftyoneDegreesResultsHashFromEvidence()

void fiftyoneDegreesResultsHashFromEvidence ( fiftyoneDegreesResultsHash * results,
fiftyoneDegreesEvidenceKeyValuePairArray * evidence,
fiftyoneDegreesException * exception )

Processes the evidence value pairs in the evidence collection and populates the result in the results structure.

The result shape is a deterministic function of the data set, not of how many evidence pairs are supplied. One result item is produced per available component (results->count == componentsAvailableCount when every available component resolves from the evidence, as it does for a User-Agent). Adding a redundant, lower-precedence pair that resolves to the same value (for example both 'query.user-agent' and 'header.user-agent') therefore does not change the number or layout of result items. This is the single detection entry point; ResultsHashFromUserAgent is a thin wrapper over it.

Each available component with evidence for one of its headers takes a result, in component order. When the caller named the properties the data set was created with, the graph of each of those components is walked here, so no read walks a graph and the results keep no copy of the evidence. Otherwise no graph is walked here. The evidence is copied into the results, and a component's graph is walked the first time one of its properties is read. A device id in the evidence sets every profile here, and profile overrides and default profiles are applied as they are once every graph has been walked, so the answers do not depend on what is read first. The evidence can be freed once this returns. Code that reads the result items directly, such as their match metrics, calls fiftyoneDegreesResultsEvaluateAll first.

The 'query' and 'cookie' evidence key prefixes are used to get values which dynamically override values returned from device detection. 'query' prefixes are also used in preference to 'header' for HTTP header values that are provided by the application rather than the calling device. 'query.51D_deviceId' special evidence key has the highest priority and allows to retrieve the designated device by its 'deviceId'. 'deviceId' value is obtained as a property in the device detection results and may be stored and used later to retrieve the same device. In case provided 'query.51D_deviceId' value is invalid or does not match any device the other provided evidence will be considered.

Parameters
resultspreallocated results structure to populate containing a pointer to an initialised resource manager
evidenceto process containing parsed or unparsed values
exceptionpointer to an exception data structure to be used if an exception occurs. See exceptions.h.

◆ fiftyoneDegreesHashBalancedConfig

EXTERNAL_VAR fiftyoneDegreesConfigHash fiftyoneDegreesHashBalancedConfig

Uses caching to balance memory usage and performance.

A connection is maintained to the source data file to load data into caches when required. As the cache is loaded, memory will increase until the cache capacity is reached. The components, maps, properties and root nodes are held in memory. The concurrency of each collection must be set to the maximum number of concurrent operations to optimize file reads. This is the default configuration. In this configuration, both the performance and predictive graphs are enabled, as performance is not as big of a concern in this configuration, so falling back to the more predictive graph if nothing is found on the first pass can be afforded.

Default detection configuration.

This configures the data set to not create a temp file, make no allowance for drift and difference and record the matched User-Agent substrings. In this configuration, both the performance and predictive graphs are enabled, as performance is not as big of a concern in this configuration, so falling back to the more predictive graph if nothing is found on the first pass can be afforded.

◆ fiftyoneDegreesHashHighPerformanceConfig

EXTERNAL_VAR fiftyoneDegreesConfigHash fiftyoneDegreesHashHighPerformanceConfig

Highest performance configuration.

Loads all the data into memory and does not maintain a connection to the source data file used to build the data set. The concurrency setting is ignored as there are no critical sections with this configuration. In this configuration, only the performance optimised graph is enabled for processing to give the fastest operation.

It sets loadRequiredPropertiesOnly, so when the required properties name some but not all of the properties in the data file, only the values they read and the strings those values use are kept in memory, and the rest of the values and strings read from the data file.

◆ fiftyoneDegreesHashLowMemoryConfig

EXTERNAL_VAR fiftyoneDegreesConfigHash fiftyoneDegreesHashLowMemoryConfig

Low memory configuration.

A connection is maintained to the source data file used to build the data set and used to load data into memory when required. No caching is used resulting in the lowest memory footprint at the expense of performance. The concurrency of each collection must be set to the maximum number of concurrent operations to optimize file reads. In this configuration, both the performance and predictive graphs are enabled, as performance is not as big of a concern in this configuration, so falling back to the more predictive graph if nothing is found on the first pass can be afforded.

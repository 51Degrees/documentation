How we tested🔗

We ran the Device Detection C library on seven machines, from a 128-core server down to a desktop PC built in 2008, and the IP Intelligence C library on five of them. We recorded throughput, startup time, and memory use on each. Every machine used the same library versions, data files, and evidence, and we ran each test once.

Libraries and data🔗

We built the C libraries from the public repositories, at version 4.5.70 for Device Detection and 4.5.34 for IP Intelligence. Each machine compiled its own Release build with -O3. The build script also adds -march=native, dropping it if the compiler rejects it. The machines table lists each compiler.

The data files were TAC-HashV41.hash (99,667,840 bytes) for Device Detection and 51Degrees-IPIV4EnterpriseIpiV41.ipi (6,121,965,416 bytes) for IP Intelligence, both published on 30 July 2026.

Configurations🔗

Each library ran in two configurations:

  • InMemory loads the whole data file into memory. It is the configuration that the MaxPerformance profile selects. For these runs we also compiled the library with the memory-only option (FIFTYONE_DEGREES_MEMORY_ONLY), which leaves out the code for reading from disk.
  • Balanced, the default profile, reads most of the data file through caches that keep the most used data in memory and leave the rest on disk. For IP Intelligence, Balanced still loads some parts of the data file fully into memory, including the text strings and the IP address graphs described in IP Intelligence Algorithm. Each Balanced run made an untimed warm-up pass over the same records it then timed, so the caches had already seen that traffic. We set the expected concurrency to the number of threads, as Concurrent Processing describes. On the Dell server, with 128 threads, that raised every cache smaller than 16,384 entries to 16,384.

Properties🔗

The IsMobile, PlatformName, BrowserName, and IsCrawler columns each request that property alone. In that order, they come from the hardware, operating system, browser, and crawler components. "One per component" requests all four properties together, and "Every property" requests all 279. For IP Intelligence, the RegisteredName, AsnName, and Longitude columns each request that property alone. "All three" requests them together, and "Every property" requests all 49.

Requesting fewer properties is faster because each detection has fewer values to read, and for Device Detection the library evaluates only the components that the requested properties belong to (see Restrict properties).

Evidence🔗

Device Detection used six million sets of HTTP request headers from real web traffic. Each set has a User-Agent, plus User-Agent Client Hints where the browser sent them. Popular devices and browsers appear many times.

IP Intelligence used six million IP addresses from real web traffic, with no address repeated in the set.

Each machine ran one thread per logical processor, and each thread took its own share of the records. In the timed pass every record was processed once, and no results cache was used. The InMemory runs timed all six million records and the Balanced runs timed the first one million. The one exception is the Balanced every-property run, which was limited to 20,000 records because reading every property with Balanced is very slow. Each thread's share of that limit was rounded up to a whole number of records, which made the totals 20,096 on the Dell server and 20,004 on the 2018 Mac mini.

Reading the tables🔗

Detections per second is the total number of records that all the threads processed, divided by the wall-clock time from the first thread starting to the last one finishing. A detection here means taking one record, finding the result, and reading every requested property value. The IP Intelligence tables count lookups per second in the same way, where a lookup finds the properties for one IP address. Loading the evidence into memory happened before the clock started and isn't included.

Startup is how long it took to load the data file and be ready to detect, with every property requested.

Dataset memory is how much the process's resident memory grew when the data file was loaded, before any detections ran. It doesn't include the evidence, and for Balanced it doesn't include the caches as they fill up. MB means 1,048,576 bytes. Four of the InMemory results showed no growth at all, which can't be right when the whole file is loaded, and the tables show n/a for those. Only the memory reading is in doubt, because checksums of the detection results from those runs match those from the other machines.

To work out how long one detection takes with every thread busy, divide the number of threads by the detections per second, because each thread handles its records one after another. On the Graviton3 instance with InMemory and IsMobile, eight threads at 1,362,952 detections per second works out at about 5.9 microseconds per detection.

What we didn't measure🔗

  • Which machines kept -march=native.
  • A standard build using MaxPerformance, which may be slower than the InMemory figures here.
  • Memory use once the Balanced caches had filled.
  • How much results vary from one run to the next, because each test ran once.
  • What effect the intermittent low-voltage warnings we saw during the Raspberry Pi run had on its results.
  • IP Intelligence on the Raspberry Pi and the 2008 desktop. The IP Intelligence InMemory run needs 5,838 MB, which is more memory than either machine has, so we left the whole product out on both. That includes the Balanced run, even though Balanced needs less memory.
  • Why the 128-core server was slower than the eight-core Graviton3 instance in every Balanced column.
